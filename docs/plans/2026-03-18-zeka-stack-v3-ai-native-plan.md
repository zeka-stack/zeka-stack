# Zeka Stack v3.0.0 规划设想

## 背景

最近我一直在重新思考一个问题：当 AI 已经越来越擅长写代码时，我继续做一套基于 Spring Boot 的脚手架，到底还有什么意义？

如果脚手架的价值仍然停留在“帮开发者少写几行样板代码”，那么它的价值确实正在被快速削弱。因为现在的大模型已经可以生成 Controller、Service、DTO、Mapper，甚至连测试代码、文档和脚本都能一并产出。过去脚手架解决的是“代码写得慢”的问题，而今天这个问题正在被 AI 迅速吞掉。

但我认为，这并不意味着脚手架没有价值了。恰恰相反，AI 越强，工程体系、规则体系、契约体系和治理体系就越重要。AI 可以高效地产生代码，但它不会天然理解团队的架构边界，不会天然遵守我的分层规范、日志规范、异常规范、依赖约束、发布要求和安全边界。它能写得很快，但未必能写得长期可维护。

所以我对 Zeka Stack 的判断是：`v3.0.0` 不能再被定义为一次普通的脚手架升级，而应该被定义为一次面向 AI 时代的重新定位。

## 我的核心判断

我希望 Zeka Stack 从“Spring Boot Starter 集合”演进为“AI Native 的 Java 工程平台”。

这里的重点不再只是“快速起项目”，而是三件更有长期价值的事：

1. 让 AI 能够参与开发，但必须沿着我定义的工程轨道前进。
2. 让后端系统输出的不再只是给人看的接口文档，而是能被 AI 直接理解和消费的业务契约。
3. 让整个工程天然具备接入 Agent Runtime 的能力，例如 MCP、Tools、OpenClaw 这类能力，而不是以后零散拼接。

换句话说，我不想把 `v3.0.0` 做成“AI 帮我写代码的脚手架”，而是要做成“让 AI、开发者和业务系统可以协同工作的工程底座”。

## 我对 v3.0.0 的定位

我准备将 `Zeka Stack v3.0.0` 定义为：

`AI Native Spring Boot Engineering Platform`

这个定位至少包含三个层面。

### 1. AI Assisted Development

第一层是让 AI 参与开发。  
但我不希望这种参与只是“把仓库丢给大模型，然后让它自由发挥”。我希望 AI 是在明确规则、清晰边界和固定工作流之下参与开发。

因此，`v3.0.0` 需要把过去隐含在我脑子里、散落在项目里的经验，沉淀为一套可执行、可复用、可学习的 AI 开发资产。这些资产应该包括：

- 项目级规则：分层约束、命名约定、异常处理、统一响应、日志规范、测试规范、模块依赖方向等。
- Skills：围绕 Zeka Stack 仓库开发的技能包，例如新增 Starter、补充文档、生成示例工程、完善测试、检查依赖边界等。
- MCP 能力：把项目结构、模板、规范、命令、示例、依赖关系暴露给 AI 作为稳定工具能力。
- AI 工作流样板：向外部使用者展示如何在 Zeka Stack 中合理地引入 AI 开发，而不是停留在口头理念上。

这部分的目标不是单纯提升我个人效率，而是把“如何使用 AI 做工程化开发”这件事本身产品化、开源化。这样 Zeka Stack 才不仅是一个脚手架，也是一套可以被别人学习和复用的 AI 开发方法论。

### 2. AI Consumable Backend Contract

第二层是让后端对 AI 友好。  
这是我认为 `v3.0.0` 最核心的一次升级。

当前很多项目里的 Swagger、Knife4j、本质上仍然是给人看的。它适合开发者浏览接口、调试参数、查看返回结构，但它不天然适合 AI 做更深入的理解。因为对 AI 来说，光有接口路径、字段类型和简单描述是不够的。AI 真正需要的是：

- 更强的领域语义
- 更明确的参数约束
- 更清晰的错误码和失败语义
- 更完整的输入输出示例
- 更稳定的状态流转说明
- 更贴近业务任务的接口组合关系

因此，我不希望 `cubo-openapi-spring-boot` 继续只服务“人类开发者读文档”这个目标。我希望它升级为“双轨文档体系”：

- 一条轨道继续保留给人类开发者使用的 OpenAPI / Knife4j 文档。
- 另一条轨道输出面向 AI 的 API / 业务契约。

后者不应该只是传统 OpenAPI 的简单翻版，而应该包含更适合 AI 消费的数据：

- 增强版 OpenAPI 元信息
- 字段级业务语义与约束
- 统一错误模型与恢复建议
- 面向前端代码生成的表单、列表、动作元数据
- 领域词汇表和对象关系
- 任务链路示例，例如“创建订单 -> 支付 -> 取消”的完整业务流

我的目标不是只做“更漂亮的接口文档”，而是做“AI 理解后端业务的标准契约层”。这样未来 AI 才可能更稳定地根据后端契约生成前端页面、交互逻辑和 API 调用代码。

### 3. Agent Ready Runtime

第三层是让整个工程天然具备 Agent 集成能力。  
我希望 Zeka Stack 不只是“适合 AI 参与开发”，还要“适合 AI 作为运行时能力接入系统”。

这意味着我需要认真考虑 MCP、Tool、Session、Memory、权限控制、审计、危险操作隔离这些问题，而不是简单做几个 Demo 接口。

对于 OpenClaw，我的判断是应该把它放在一个明确的适配层，而不是直接侵入业务模块。OpenClaw 可以成为 `v3.0.0` 中的重要组成部分，但它更适合被定义为 Agent Runtime Adapter，而不是系统内核本身。

我倾向于把这部分抽象为几层能力：

- `agent-core`：统一 Tool、Agent、Session、Memory 的抽象。
- `agent-mcp`：MCP Server 和 MCP Tool 的接入与发布。
- `agent-openclaw-adapter`：与 OpenClaw 的运行时模型和技能体系对接。
- `agent-security`：审计、脱敏、危险操作确认、权限隔离。

这样设计的好处是，Zeka Stack 可以先接 OpenClaw，但不会被 OpenClaw 绑定死。未来如果要兼容其他 Agent Runtime，也不需要推翻整个架构。

## 我现在进一步意识到，AI 的范畴远不止这三点

最开始我在思考 `v3.0.0` 的时候，比较容易聚焦在几个最直观的方向上，例如让 AI 参与开发、输出 AI 友好的接口文档，以及接入 OpenClaw 之类的 Agent Runtime。但结合当前仓库现状再往回看，我越来越明确地意识到，AI Native 绝不是只加几个 AI 功能点，而是要重新设计整个工程体系与 AI 的协作方式。

更直接地说，Zeka Stack 当前已经具备不少可以向 AI 方向放大的基础能力。例如：

- `cubo-launcher-spring-boot` 已经有配置热更新和扩展点能力。
- `cubo-logsystem-spring-boot` 已经有日志动态调整和记录体系。
- `cubo-endpoint-spring-boot` 已经有项目、健康、监控、管理端点。
- `cubo-rest-spring-boot` 已经有统一异常、统一响应、参数校验等基础约束。
- `cubo-spring-boot-templates` 已经有模板化生成能力。
- `blen-kernel-generator` 已经有代码生成、模板变量和元数据注入的基础。
- `zeka-idea-plugin` 下面已经有 `intelli-ai-engine`、`intelli-ai-terminal`、`intelli-ai-swagger`、`intelli-ai-tracer`、`intelli-ai-changelog`、`intelli-ai-agent-template` 等一系列 AI 相关探索。

这说明我现在要做的，不是从零给项目“加点 AI”，而是把这些分散存在的能力提升到统一架构和统一产品叙事之下。

## 我认为 Zeka Stack 3.0 还应该覆盖的 AI 方向

### 1. AI First Scaffold

我不希望脚手架只生成代码骨架，而希望它生成的是“适合 AI 继续协作的工程骨架”。

也就是说，一个新模块被生成出来时，不仅要有 `autoconfigure / core / starter` 这些目录结构，还应该一并生成：

- 该模块的规则说明
- 推荐提示词和使用方式
- 最小测试用例
- 文档模板
- 契约模板
- 面向 AI 的元数据文件

这样生成出来的不是一套死模板，而是一套可持续被 AI 理解、扩展和校验的工程起点。

### 2. AI Domain Memory

如果 AI 只看 Controller 和 DTO，它理解到的仍然只是表层结构。  
我希望 Zeka Stack 可以沉淀出一层领域记忆，让 AI 真正理解业务语言。

这层内容可以来自：

- 表结构和字段注释
- 枚举定义
- 错误码
- README 和模块文档
- 示例工程
- 业务对象之间的关系

最后形成的是一份项目级领域词典，甚至是一套轻量知识图谱。这样 AI 理解的不只是“这个字段叫 `status`”，而是“这个状态有哪些取值、对应什么业务阶段、会影响哪些接口和页面动作”。

### 3. AI Config Copilot

当前很多 AI 场景只盯着业务代码，但在真实工程里，配置同样是高频且高风险区域。  
而 Zeka Stack 已经有配置热更新、环境感知和配置扩展点，这其实非常适合演进成“配置协作能力”。

我希望未来 AI 能够：

- 解释某个配置项的作用和影响范围
- 分析配置变更会影响哪些 Bean、模块和接口
- 对配置 diff 做风险提示
- 给出环境迁移建议
- 结合 Nacos / 本地配置进行统一解释

这类能力对团队日常开发和运维协作的价值，未必低于代码生成。

### 4. AI Ops Copilot

Zeka Stack 现在已经有日志系统、健康检查、项目端点、监控入口、APM 和链路追踪方向。  
这意味着它完全可以不只做“开发期 AI”，还可以做“运行期 AI”。

我希望 AI 最终能参与这些事情：

- 读取启动信息和健康状态并做诊断
- 分析日志并给出故障定位建议
- 基于 tracing / APM 数据解释一次请求链路
- 辅助定位配置错误、依赖冲突、超时和线程问题
- 生成标准化故障摘要

如果这一层做好，Zeka Stack 的 AI 价值就不只在写代码，而是在整个应用生命周期里都能提供帮助。

### 5. AI Contract + Frontend Manifest

接口文档 AI 友好化只是第一步。  
真正更有价值的是输出一层更适合前端生成的清单，也就是 Frontend Manifest。

这一层不只是接口，而是围绕页面和交互建模，例如：

- 页面有哪些资源对象
- 列表页展示哪些字段
- 表单有哪些输入项和校验规则
- 每个状态下允许哪些操作
- 错误时前端应该如何提示
- 枚举值应该如何渲染

如果这一层可以稳定输出，那么 AI 才有可能更可靠地从后端契约生成前端页面，而不是每次都靠大模型临场猜测。

### 6. AI Test / Eval Platform

AI Friendly 不能只看“能不能生成”，还要看“生成质量是否稳定”。  
所以我认为 `v3.0.0` 必须补上一套评测与验证视角。

至少要能回答：

- AI 生成的模块是否遵守分层规范
- AI 生成的接口是否满足响应和错误约定
- AI 生成的测试是否覆盖关键路径
- AI 生成的前端是否能正确消费契约
- Agent 调用是否越权、是否缺少审计

没有评测体系，所谓 AI Native 最后往往会变成一堆 Demo，而不是稳定的工程能力。

### 7. AI Release Copilot

我在 `zeka-idea-plugin` 中已经有 changelog、diff、prompt、版本解析等能力探索。  
这说明发布协作本身就是一个非常适合 AI 切入的方向。

未来我希望 Zeka Stack 能支持：

- 根据代码 diff 自动生成发布说明草稿
- 分析本次版本影响到哪些模块
- 判断哪些 starter 和下游示例需要联动验证
- 给出升级风险与迁移提示
- 输出面向人类和面向 AI 的两套变更摘要

这样 `v3.0.0` 就不仅是开发框架，也会是版本治理平台。

### 8. AI Runtime / Agent Platform

OpenClaw 只是入口，不应该是全部。  
更完整的方向应该是把 Zeka Stack 演进成一套统一的 Agent 能力底座。

我已经有 `intelli-ai-agent-template` 这类实践，说明在协议适配层已经有了一定基础。  
接下来更值得做的是统一抽象：

- Tool 定义
- MCP 能力发布
- OpenAI Compatible Adapter
- Agent 权限与审计
- 会话与记忆边界
- 危险操作确认机制

这样未来不管接 OpenClaw，还是接其他 Runtime，底座都不会变形。

## 对现有模块的迭代想法

结合当前仓库结构，我认为 `v3.0.0` 的改造不应该平均用力，而应该围绕几个关键模块集中突破。

### supports

`supports/` 不应该只继续承担脚本和资源目录的角色，而应该升级成整个 AI 开发能力的总入口。

我希望这里逐步沉淀出：

- `supports/ai/rules/`
- `supports/ai/skills/`
- `supports/ai/mcp/`
- `supports/ai/prompts/`
- `supports/ai/playbooks/`
- `supports/ai/evals/`
- `supports/ai/domain-memory/`
- `supports/ai/release/`

以后别人学习如何在一个开源 Java 项目里系统化使用 AI，第一站应该就是这里。

### cubo-spring-boot-templates

我现在认为这个模块不应该只是“创建模块的命令行工具”，而应该升级为 `AI First Scaffold` 的入口。

也就是说，它不仅生成目录和 POM，还应该输出：

- 模块规则说明
- 契约模板
- 测试模板
- 示例调用
- 面向 AI 的元数据

未来如果要做“用一句自然语言描述一个 starter，然后自动生成第一版模块骨架”，这里会是很自然的落点。

### cubo-openapi-spring-boot

这个模块应该成为 `v3.0.0` 的核心改造点。  
我会保留它现有的人类文档能力，但同时让它具备输出 AI 契约的能力。

我暂时不想只做一个“AI 注释增强器”，因为那样价值不够大。我更希望把它做成一个契约层产品，甚至可以考虑重新命名，或者在现有模块下扩出新的 AI 子模块。

### cubo-rest-spring-boot

如果后端要被 AI 更好理解，那么 REST 层的表达必须更规范。  
统一响应、错误码、分页语义、幂等语义、鉴权语义、状态约束，这些都要形成稳定模型。否则 AI 消费文档时仍然会面临大量歧义。

除此之外，这里还适合继续往“任务级语义”推进，例如：

- 列表查询的通用过滤结构
- 分页和排序契约
- 批量操作契约
- 幂等语义
- 长任务和异步任务响应模型

这些内容一旦稳定下来，就不仅方便 AI，也会反过来提升整套 REST 体系的一致性。

### blen-kernel

这里适合承接一些跨模块的底层抽象，例如：

- 统一错误模型
- 领域词汇与语义抽象
- 审计模型
- Agent 相关基础接口
- AI 友好的元数据结构
- 领域词汇表模型
- 配置语义模型
- 契约扩展注解

### domi-suite / felo-space

我不希望 AI Friendly 只停留在概念层。  
因此我需要用真实业务样例来证明这套设计是可落地的。`domi-suite` 和 `felo-space` 正好可以承担这个角色：不仅展示后端能力，还展示如何基于 AI 契约驱动前端生成和 Agent 集成。

除此之外，我还希望它们承担另外两个职责：

- 作为 AI 运维诊断样板，验证日志、端点、配置、追踪协作能力。
- 作为评测样板，验证 AI 生成页面、生成测试、生成文档时的效果和偏差。

### cubo-launcher / cubo-logsystem / cubo-endpoint

我现在认为这三个模块应该一起看，而不是分开看。  
因为它们天然构成了 Zeka Stack 做 `AI Ops Copilot` 的基础设施。

- `cubo-launcher` 适合承接配置解释、热更新分析、启动期上下文。
- `cubo-logsystem` 适合承接日志理解、日志级别建议、故障摘要。
- `cubo-endpoint` 适合承接健康状态、项目状态、诊断和安全管理入口。

如果这三层联动起来，AI 在运维侧就不再是“外部聊天助手”，而是项目内生的协作能力。

### zeka-idea-plugin

IDEA 插件未来仍然有价值，但我认为它在 `v3.0.0` 中不应该抢主线。  
短期内更重要的是先把规则、契约和运行时边界打稳。等这些能力稳定后，再考虑把它们封装进插件，做成本地研发入口。

不过，从现在仓库情况看，插件侧已经不应该被简单理解为附属品。  
它其实已经是一个非常重要的验证场：`intelli-ai-engine`、`intelli-ai-terminal`、`intelli-ai-tracer`、`intelli-ai-changelog`、`intelli-ai-swagger`、`intelli-ai-agent-template` 这些模块说明我已经在 IDE 协作、终端协作、工作流解释、发布协作、协议适配等方向做了不少探索。

因此更合理的策略不是“插件先放着”，而是把插件层当成 Zeka AI 能力的前端入口和实验场，再把稳定能力沉淀回总仓库规范中。

## 我对 v3.0.0 的阶段性路线

我不打算在一个版本里同时把所有事情做完。  
`v3.0.0` 更适合按阶段推进，而不是一次性铺开。

### P0：先完成 AI 工程规范化

这一阶段优先解决“如何让 AI 进入 Zeka，并且不把工程搞乱”。

我希望至少交付：

- 一套项目规则库
- 一批围绕仓库开发的 skills
- 一个最小可用的 MCP 能力集
- 一套评测样例和校验规则
- 面向开源用户的 AI 开发示例工作流

这一步是整套 `v3.0.0` 的地基。没有这一层，后面的契约、前端生成、Agent 集成都会变得不稳定。

### P1：补齐 AI Contract 与领域记忆

这一阶段不只重构 OpenAPI，还要把“AI 理解业务”这件事一起做起来。

我希望做到：

- 保留原有人类文档能力
- 输出增强的 AI 契约
- 沉淀领域词典和业务语义
- 统一错误语义与状态语义
- 提供任务型示例

这样 AI 看到的不只是接口，而是一套更完整的业务表达。

### P2：扩展到 AI Frontend 与 AI Ops

当前很多框架都在谈“AI 生成页面”，但我认为更现实的做法是同时推进两条线：

- 一条线是 Frontend Manifest，让 AI 更稳定地生成前端代码。
- 一条线是 Ops Copilot，让 AI 能理解配置、日志、端点和运行状态。

如果这一步能落地，Zeka Stack 的 AI 能力就会从开发期扩展到运行期。

### P3：集成 OpenClaw 与 Agent Runtime

等前面几层基础稳定后，再正式引入 OpenClaw 和更完整的 Agent Runtime 能力。

这一阶段更关注：

- 统一工具抽象
- OpenClaw 适配
- MCP 联动
- 审计与权限边界
- 会话与记忆边界
- 可演示、可扩展、可治理

## 我希望 v3.0.0 最终达到的状态

我希望 `v3.0.0` 完成后，Zeka Stack 至少具备下面几个结果：

1. 开发者可以基于 Zeka 的规则、skills 和 MCP，让 AI 参与一个真实模块的开发。
2. 后端可以输出不只是给人看的 Swagger 文档，而是给 AI 消费的业务契约。
3. 项目能够沉淀领域词典、错误语义、状态语义等 AI 可复用的知识资产。
4. 至少有一个真实业务样例，可以由 AI 根据契约半自动生成前端代码。
5. AI 能够辅助解释配置、日志、健康状态和基础运行问题。
6. 至少有一条 OpenClaw 集成链路能够跑通，并带有明确的权限和审计边界。

如果这些目标能够落地，那么 `v3.0.0` 的价值就不再是“我又做了一套脚手架”，而是“我重新定义了一套适合 AI 时代的 Java 工程底座”。

## 最后

我现在越来越明确地认为，AI 并没有让脚手架失去意义，而是逼着脚手架升级。

过去脚手架解决的是模板和样板代码问题，未来脚手架真正要解决的，是工程规则沉淀、业务契约表达、AI 协作方式、Agent 运行边界这些更高层次的问题。

从这个角度看，Zeka Stack `v3.0.0` 不应该只是一次版本升级，而应该是一次定位升级：

从 Spring Boot Starter 体系，走向 AI Native 的工程规范平台、AI 可消费的业务契约平台、AI 运维协作平台，以及 Agent 集成底座。
